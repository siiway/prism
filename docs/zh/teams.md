# 团队

团队是 OAuth 应用与已验证域名的共同所有者。成员在与个人资源相同的界面中管理团队的应用和域名，且归属不会因任何单个成员的离开而消失。

## 角色

| 角色       | 管理成员         | 编辑团队设置 | 管理应用/域名            | 转移所有权           | 解散 |
| ---------- | ---------------- | ------------ | ------------------------ | -------------------- | ---- |
| `owner`    | 是               | 是           | 是                       | 是（转给共同所有者） | 是   |
| `co-owner` | 是（所有者除外） | 是           | 是                       | 否                   | 否   |
| `admin`    | 是（仅限成员）   | 否           | 是                       | 否                   | 否   |
| `member`   | 否               | 否           | 读取；团队允许时可写应用 | 否                   | 否   |

每个团队只有一名所有者。转移所有权会将原所有者降级为共同所有者。

站点管理员对每个团队拥有所有者级权限。参见[管理 → 团队](admin.md#团队)。

## 加入团队

1. **直接添加** —— 由管理员、共同所有者或所有者通过 **团队 → \<team\> → 成员 → 添加成员** 添加。
2. **邀请链接** —— 通过 **成员 → 生成邀请** 生成，可选锁定到某个邮箱地址、限制使用次数并设置过期时间。链接会打开 `/teams/join/:token`，在用户接受前展示团队信息以及任何未满足的[加入门槛](#加入门槛)。
3. **API** —— `POST /api/teams/join/:token`。

管理员可以编辑、禁用或撤销自己创建的邀请；共同所有者与所有者可以管理团队的全部邀请。使用次数上限不能降低到当前已使用次数以下。邀请还可以携带一个[身份组](#身份组)，在用户加入时自动分配。

## 加入门槛

团队所有者可以要求成员具备：

- 至少一个 TOTP 认证器或 Passkey，和/或
- 已验证的主邮箱。

站点管理员可以设置适用于所有团队的最低要求；所有者可以要求更多，但绝不能更少。站点强制的要求在团队设置页中会置灰。

::: warning 回溯生效
启用某项门槛会立即对现有成员生效。未满足要求的成员会在补齐之前被拦在团队操作之外。开启前请先通知成员。
:::

## 子团队

团队可以创建在另一个团队之下，以映射组织结构。嵌套受站点最大深度限制（默认 5），且不能以会形成循环的方式移动团队。

有两样东西会从团队向下传递给其下所有层级，且每一项都可以由站点管理员关闭：

- **成员资格** —— 团队成员在其每个子团队上至少拥有相同角色。子团队上的直接角色会叠加，取较高者。
- **已验证域名** —— 子团队会以只读条目看到其祖先团队的域名，且祖先已验证域名的子域名会自动通过验证。

应用仍归属于创建它的团队。

在 **团队 → \<team\> → 子团队** 中管理子团队。创建子团队时，你需要是父团队（直接或继承）的管理员或更高角色。将团队移动到新的父团队，需要你是该团队的所有者，并且是新父团队的管理员。删除团队会删除其下每个子团队；每一层的应用会归该层自己的所有者。

### 成员列表可见性

在 **设置 → 成员列表可见性** 中，所有者与共同所有者可以限制普通成员能看到的内容：仅限所有者、共同所有者、管理员和成员本人。这同样适用于团队公开资料以及读取成员列表的应用。

## 身份组

身份组是附加在成员上的标签，一个成员可以持有多个。它们永远不会改变任何人在 Prism 内能做什么。它们会随成员信息一起传递给团队接入的应用，供这些应用据此做决策。

默认关闭；由团队所有者在 **设置 → 身份组** 中开启。

### 身份组还是子团队？

需要拥有独立页面、应用、域名和角色的独立单元时，用**子团队**。要给同一批人的某个属性打标签（例如 `oncall`），用**身份组**。拿子团队当标签用，每个标签都会让 claims 里多出一个团队；而且由于成员资格会向下传递，你本来只想打标签的人也会在那里获得角色。

### 定义与分配

在 **团队 → \<team\> → 身份组** 下定义身份组：

| 字段 | 说明                                               |
| ---- | -------------------------------------------------- |
| Slug | 应用用于校验的值。之后不可修改，以免打断现有策略。 |
| 名称 | 展示标签；可编辑。                                 |
| 描述 | 可选。                                             |
| 颜色 | 可选，用于徽章的 `#rrggbb`。                       |

限额：每个团队 50 个身份组，每个成员 20 个；slug 最长 32 个字符，仅限小写字母、数字和单个连字符。

在成员行上的标签按钮处分配身份组。所有者与共同所有者始终可以定义和分配。对于管理员，由所有者决定其能否**管理**身份组（默认关闭）和**分配**身份组（默认开启），并可将某个特定身份组保留给所有者。只有所有者能修改这些设置。

身份组会像角色一样向下传递给子团队，并在其来源团队处管理。

关闭身份组是隐藏而非删除：已接入的应用会从下一次令牌刷新起看不到它们，重新开启后会恢复所有分配。删除某个身份组或关闭该功能，只会让下游访问变得更严格。

### 应用在哪里看到

身份组会出现在应用已有权读取的团队成员信息中（`team:<id>:member:read`、`team:<id>:member:profile:read`），并以 `groups_in_team_<id>` 的 slug 数组形式出现在 ID 令牌中。无需额外的 scope 或授权；管理仅在仪表盘中进行。

## 邀请链接注册

通常团队邀请只会让已有 Prism 账号的人加入。经站点管理员授权的团队，还可以通过 `/join/<team-id>` 页面发放能创建账号的链接。这些账号是**受限**的（见下文），因此大规模、用途单一的人群可以登录，而无需让每个人都能创建团队、应用和域名。

要使用该功能，需由站点管理员在团队的**管理**标签页中授予该能力。团队所有者无法自行授予。然后在生成邀请时勾选 **可用于创建新账号**。这类邀请：

- 必须设置有限的使用次数，且低于站点上限（默认 1000）；
- 始终授予 `member` 角色；
- 在常规的按 IP 限流、验证码和工作量证明之外，还会按小时限流（默认 200）。

注册者的账号初始为 pending 状态。它可以管理自身安全设置（以配置 2FA 或验证邮箱），但在满足团队门槛并加入之前，无法登录任何应用。未完成的注册默认在 72 小时后删除。名额在账号创建时即被占用，因此被放弃的注册仍会计入上限。

如果站点管理员为该团队豁免邮箱验证，注册表单不会索要邮箱地址。账号会得到一个占位地址，用户必须在转换为完整账号前添加真实地址。

## 受限账号

通过邀请链接创建的账号是受限的。默认情况下，它们**不能**创建团队或应用、验证域名、创建个人访问令牌或 GPG 密钥、发布公开资料，或转换为完整账号。团队功能与自身账号安全始终可用。站点管理员可以逐项放开能力（参见[配置](configuration.md#邀请链接注册)）。

受限账号被限制在其**来源团队及该团队的子团队**内：只能加入这些团队，且只能登录它们拥有的应用。加入其他团队不会扩大这一范围。

**转换** —— 在允许的情况下，用户可在 **安全 → 账号类型** 处转换。转换需要已验证的真实邮箱，会保留其团队成员身份，解除所有限制，且不可撤销。站点默认值可在团队的**管理**标签页中按团队覆盖。

**解散**创建过账号的团队会删除这些账号，因此只有站点管理员可以执行，且需经过带宽限期的分阶段流程（参见[管理 → 邀请链接注册](admin.md#邀请链接注册)）。只要团队仍有存活的受限账号，它就不能被常规删除，即使授权已关闭。已转换的账号以及使用自己账号加入的成员不会被删除。

## 团队拥有的应用与域名

可在 **团队 → \<team\> → 应用 → 新建** 中于团队下创建应用，或从个人应用转入（**应用 → \<app\> → 设置 → 转移**）。转入的应用会保留其客户端 ID 与密钥，因此集成不会中断。

只有团队管理员或更高角色可以创建应用或轮换其密钥。密钥仅在创建或轮换时显示一次。

个人域名可以共享给团队，之后移回，或完全转移给团队。

## 团队公开资料

团队默认私密。所有者或管理员在 **设置 → 公开资料** 中启用，并选择要展示的区块。参见[公开资料](public-profile.md)。

## OAuth scope

涉及团队的 scope 分为三个系列。选择能满足需求的最窄一个。

| 系列          | 示例             | 覆盖范围                   | 谁可以授予                         |
| ------------- | ---------------- | -------------------------- | ---------------------------------- |
| `teams:*`     | `teams:read`     | 用户所属的每个团队         | 用户本人                           |
| `team:*`      | `team:read`      | 在授权页面上选定的单个团队 | 该团队的所有者、共同所有者或管理员 |
| `site:team:*` | `site:team:read` | 实例上的每个团队           | 站点管理员，需经过 2FA 确认        |

- **`teams:*`**（`read`、`write`、`create`、`delete`）适用于工作区选择器、成员同步，以及为 Cloudflare Access 之类的工具提供 ID 令牌 claim。
- **`team:*`**（`read`、`write`、`delete`、`member:read`、`member:write`、`member:profile:read`）绑定到用户选定的团队，因此令牌只能操作该团队。`team:delete` 需要所有者或共同所有者，且 `team:member:write` 不能把任何人提升到超出授权用户自身权限的范围。
- **`site:team:*`** 仅用于站点管理工具。参见 [OAuth → 站点 scope](oauth.md#站点-scope)。

不要同时请求 `teams:*` 和 `team:*`；那样授权页面会同时显示全团队提示和团队选择器，让用户困惑。

ID 令牌会携带 `in_team_<id>`、`role_in_team_<id>` 和 `groups_in_team_<id>` claims，供策略使用。参见 [OAuth → ID 令牌](oauth.md#id-令牌) 与 [Cloudflare Access 集成](oauth.md#cloudflare-access)。
